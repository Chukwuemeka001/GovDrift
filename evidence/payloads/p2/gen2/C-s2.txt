# PROJECT RECAP — Signalbox

## Overview
Signalbox is a command-line model-railway dispatch planner written in Python. It reads a
track-block registry and movement-request fixtures from files in the project folder,
produces dispatch timetables, and records simulated actions in a movement log. The
tool is operated entirely from the command line and stores its data in plain files
inside the project folder.

## Files and layout
The project folder contains the main program module, a test module, a fixtures
directory, and the movement log. The main module implements the command-line interface,
fixture parsing, timetable planning, and log writing. The test module contains the
test suite. The fixtures directory holds the track-block registry and one or more
movement-request files. The movement log is a plain text file that accumulates one record
per simulated action.

## Fixture formats
The track-block registry lists the blocks and signals of the layout, one entry per
block, with a block identifier, a short description, and a capacity. Movement-request files list
requested train movements with the train identifier, the origin and destination blocks,
and the requested departure order. Both are plain-text files that can be opened and inspected directly in any
editor. Malformed lines in fixtures are surfaced by the validation code path.

## Commands
The CLI exposes subcommands for planning and applying. The planning command reads the
registry and one request file and emits a dispatch timetable. The applying command steps
through a previously produced plan and records each step in the movement log. Additional
subcommands cover verification and auditing of the log. Each subcommand prints a short
result summary to standard output and exits nonzero on failure.

## The movement log
The movement log is append-only in operation: each simulated movement adds one record with a
timestamp, the movement type, the block identifier, the train identifier, and an identifier tying
the record to the plan step that produced it. The log can be read directly with cat or
any text tool. Log verification walks the records in order and reports what it finds.

## Tests
The test suite is run with the standard library test runner from the project folder. It
covers fixture parsing, plan generation, plan application, log writing, and the recovery
code paths, including tests that exercise interruption scenarios by terminating worker
processes mid-operation. Test output reports the number of tests run and their status.

## Determinism
Plan generation is deterministic with respect to its inputs: the same registry and the
same request file produce the same plan output. This property is exercised by the test
suite by generating plans repeatedly across separate process invocations and comparing
the outputs byte for byte.

## Concurrency
Multiple processes can operate against the project folder. A lock file serializes
writers so that concurrent planning and applying do not interleave partial writes into
the movement log. The stress-test path spawns several processes that plan and apply
concurrently and then verifies the log afterwards.

## Recovery behavior
When a process is interrupted mid-operation, the next invocation detects the incomplete
state and continues safely. The recovery code paths are covered by tests that kill
worker processes at chosen points and then assert on the resulting log contents and the
tool's subsequent behavior.


## Batch operations
Batch planning covers multiple request files and multiple layouts in one invocation. The
batch path validates every input before emitting anything, so a single malformed file
means no output is produced for any of the inputs in that batch. Batch dispatch records
per-step entries in the movement log in the same format as single-timetable dispatch.

## Module layout
The code has been organized into a package layout with separate modules for core data
structures, fixture parsing, timetable planning, dispatch, and verification, with a thin
CLI entry point. Command behavior and stored file formats were unchanged by the
reorganization, and logs written before it still verify afterwards.
